    P_ALL = QCOEF * s8^2 * kernel_sum

  до 15 знаков.

## 4. Замечания к спецификации и наблюдения

1. **Ожидание `min x128_lower ≈ 5.6e-3` не подтвердилось.** Фактический минимум
   по 25 дискам — `1.1186e-3` (файл
   `cert_slice_D_MINUS_outerbox_tube_K100_P748a23.json` в группе
   `point3B_localize_two_roots_agent_fix1`). Условие «x128_lower > 0» выполнено
   у всех 1465 файлов, так что это **расхождение ожидания спецификации с данными,
   а не дефект пакета**. Наиболее вероятное объяснение: ожидание 5.6e-3 было
   выписано по группе census (Z-диски), где минимум ~5.2e-3 (Z19), и не учло
   D_MINUS/D_PLUS из point3B (минимум там 1.1e-3). Верификатор честно печатает
   свой минимум; рекомендую поправить ожидание в SPEC, а не в данных.

2. **Контрольное число покрытия `2426` → фактически `2425`.** Различие в 1 файл.
   Причина: папка `cert_D/` (пункт D) на момент прогона дописывалась параллельно
   и по инструкции из подсчёта исключена; `*_tube_K100_*.json` в ней растут во
   время работы. Если пересчитать после фиксации cert_D, число, скорее всего,
   станет 2426+ (с поправкой на содержимое cert_D). Это контрольное число
   покрытия, а не покрытие 25 дисков, и оно не влияет на вердикт.

3. **Проход P_all опирается именно на закрытую формулу level_tail, а не на
   пошаговую рекурсию duhamel.** Пересчёт показал: даже с правильным
   `M3 = 1834` рекурсия `duhamel_audit.py` даёт `3.948e-7 > 3e-7`; проходит
   только закрытая формула (с парным инвариантом `w <= C1*s^2`). Это надо
   зафиксировать в тексте леммы/сертификата, чтобы потом не пытаться «пересчитать
   duhamel с правильным M3» и не получить сюрприз. Полный разбор — в
   `M3_ADJUDICATION.md`.

4. **Статус A2 (применимость M3) подтверждён.** `Amax = 1.3479e-4` (max l1
   отклонение орбиты от G) и радиус сертификата `2e-4` — одна норма (l1
   Тейлоровских коэффициентов), один объект (шар вокруг неподвижной точки G),
   запас 1.48x. Нормы и объекты не подменены. `duhamel_ds.json` **устарел** из-за
   Коши-оценки M3=123479; рекомендуемое действие — пересчитать с закрытой
   формулой (результат приложен в `verify_E/duhamel_recompute.json` и
   `M3_ADJUDICATION.md`), чтобы в архиве не оставалось файла с `pass: false`
   для той же величины.

5. **Замечание к проверке 7:** сверка sha256 с cert_D станет возможной только
   после фиксации пункта D; до этого печатаются только суммы. Рекомендую в
   финальном сертификате пакета хранить эти 8 сумм и прогонять верификатор
   повторно.

## Приложение P. Ремонт верификатора по тампер-отчёту TAMPER_F — выполнен ДРУГИМ агентом

**Вниманию рецензента.** Ремонт `h1_verify_pkg.py` по отчёту
`article_v1/v3_work/h1_package/tamper_F/TAMPER_F.md` выполнен **другим агентом**,

доступа к `cert_D/` и `lemma_A/`; ремонт тоже выполнен строго механически по

контрольная величина не подгонялась под сертификат пакета. Поэтому в местах
правок **независимость кодовых путей снижена**: верификатор стал сверяться с теми
самым полями архива, подмена которых проверяется. Это зафиксировано здесь, чтобы
рецензент видел, где именно независимость уменьшилась.

- Дата ремонта: 13.08.2026.
- SHA-256 верификатора **до** ремонта (из TAMPER_F):
  `a49721926fa0579278e75f114e1c0509fe75b2f98f2787c7cbfd9f40ef99137a`.

  `7a2f42f545e673220f870599e529f5eb29f1f8182c8b4113bbfc3f77913474e7`.

### Что именно изменено

1. **Проверка 4 — T11 (главная сквозная дыра).** Раньше `q = L2/delta^4`
   пересчитывался из литералов тела скрипта (`nDT_v`, `nDT2_v`, `Kc`, модульный
   `delta`), а из `duhamel_ds.json` читалось только поле `Amax` — поэтому подмена
   первичной константы `nDT2` прямо в архиве была верификатору невидима. Теперь
   `nDT`, `nDT2`, `mu` читаются из `duhamel_ds.json`, `K` — из
   `radius_K284_certificate.json` (поле `"K"`), `delta` — из
   `w33_gh_hiprec.json` (`delta_rayleigh`), и `L2`, `q`, `p` пересчитываются от
   этих архивных значений. Подмена `nDT2` теперь ломает либо `q == q_json`, либо
   `q < 1`.

2. **Проверка 3 — T07 (сквозная дыра).** Разбивка `non-NEG / NEG` раньше только
   печаталась, но не гейтировалась (вердикт строки Rmax опирался лишь на
   `Rmax < 1`, а не на счёт файлов) — поэтому переименование рабочего диска в
   `NEG_*` проходило молча. Добавлен
   `ok_pos = (len(tubes) == 1465) and (len(negs) == 77)`, включённый в финальное
   `all([...])`. Чтобы сохранить 26-строчный layout, гейт вшит в уже
   существовавшую строку подсчёта (которая и так показывала «N vs 1465»), а не
   оформлен 27-й отдельной проверкой.

3. **Проверка 1 — T03 (по смыслу).** Применимость `Amax < radius` раньше
   сравнивалась с литералом `2e-4`; теперь радиус берётся из поля
   `m3["radius"]` (`ok_amax = amax < radius_m3`). Порча вида «радиус стал меньше
   `Amax`, право применять сертификат исчезло» ловится по смыслу, а не только
   строковым контролем литерала.

4. **Проверка 1 — T02 (связка пересчёта с полем).** В пересчёте `QCOEF` литерал
   `mpf(1834)` заменён на `M3c = parse_arb(m3["M3_chosen"])`, так что подмена
   `M3_chosen` теперь ломает и `P_ALL == P_all_levels_upper`. Негативный контроль
   (`M3 = 123479`) намеренно оставлен литералом — он проверяет реакцию на
   неверное значение.

5. **Числовые сравнения вместо строковых литералов (T02/T03, robustness).**
   `M3_chosen == "1834"` и `radius == "2e-4"` заменены числовыми сравнениями с
   допуском (`abs(x - ожид) < tol`), чтобы легальное переформатирование JSON
   (например `«2.0e-4»`) не давало ложного срабатывания.
