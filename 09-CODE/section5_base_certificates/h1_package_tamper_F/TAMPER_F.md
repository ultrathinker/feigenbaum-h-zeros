## Разбор непойманных порч: дыра в спецификации или в реализации?

### T07 — переименование рабочего диска в `NEG_*`  (НЕ ЛОВИТ)

**Что произошло.** Один рабочий (`non-NEG`) tube-файл переименован так, что в
имени появилось `NEG_` (файл остался в той же папке, glob его по-прежнему
находит). Итог в `check3`:

```
[OK] число файлов в 5 группах (все)        total = 1542  (не изменилось)
     non-NEG (25 дисков): 1464 ; NEG-контролей: 78      (было 1465 / 77)
[OK] Rmax_upper < 1 у всех 25 дисков        got="1464 файлов"  expected="1465"
```

**Почему не поймано.** Строка `line("Rmax_upper < 1 у всех 25 дисков",
"%d файлов" % len(tubes), "1465", ok_rmax)` печатает `1464` против ожидания
`1465`, но вердикт строки — это `ok_rmax` (все Rmax<1), **а не сравнение
счёта**. Счёт `len(tubes)==1465` нигде не гейтируется. Покрытие «формально
сходится по общему числу файлов» (total=1542 защищён), а уход одной дуги в
NEG-корзину проходит незамеченным.

**Диагноз.** Дыра **в реализации** (с небольшим вкладом спецификации). SPEC
просил «напечатать разбивку по группам» и «всего 1542», но не сказал явно
«проверить, что non-NEG ровно 1465». Автор верификатора разбивку напечатал, а
гейт повесил только на `total==1542`. Это ровно «та ошибка, которую
верификатор у нас уже нашёл» (отображение без enforcement).

**Как чинится.** Одной новой строкой в `check3`:

```python
ok_pos = (len(tubes) == 1465) and (len(negs) == 77)
line("non-NEG (25 дисков) == 1465, NEG == 77",
     "%d / %d" % (len(tubes), len(negs)), "1465 / 77", ok_pos)
```
и добавить `ok_pos` в финальное `all([...])`. Этого достаточно.

### T11 — `nDT2` → 600 (спектральный радиус q > 1)  (НЕ ЛОВИТ)

**Что произошло.** В `duhamel_ds.json` поле `nDT2` изменено `193.63 → 600.0`
(при таком значении `q = L2/delta^4 ≈ 1.26 > 1`, признак сходимости исчезает).
Итог в `check4`:

```
[OK] q = L2/delta^4        got=0.42736...  expected=0.42736...
[OK] p = 1/delta^2
[OK] max(q,p) < 1          0.4274 < 1
```

**Почему не поймано.** `check4` пересчитывает `q` из **захардкоженных** в теле
скрипта констант `nDT_v = mpf("22.19")`, `nDT2_v = mpf("193.63")`, `Kc=284`,
`rho=7.5e-4`. Из `duhamel_ds.json` верификатор читает **только** `Amax`. Поля
`nDT`, `nDT2`, `mu`, `Cs_res` в архиве он не открывает вовсе. Поэтому
подмена первичной константы `nDT2` в архиве невидима: перерасчёт идёт от
литералов, а `q_json` (в `level_tail`) остался нетронутым и с литералами
совпадает.

**Диагноз.** Дыра **в реализации**. SPEC прямо требует: «пересчитать
`q = L2/delta^4`, `p = 1/delta^2` **из первичных** `nDT`, `nDT2`, `K`, `rho`,
delta» — то есть первичные константы предполагалось брать из архива. Автор
верификатора завёл их как литералы в скрипте, поэтому «первичные» для него —
это литералы, а не значения в архиве. Подмена первичной константы в архиве
проходит.

**Как чинится.** Читать первичные константы из архива и считать от них:

```python
duh = json.load(open(ARCH/"w36/audit_codex/duhamel_ds.json"))
nDT  = mpf(duh["nDT"]);  nDT2 = mpf(duh["nDT2"])
mu   = mpf(duh["mu"]);   rho  = ... # rho — из своего источника
K    = mpf(json.load(...)["K"])     # из radius_K284
delta = mpf(gh["delta_rayleigh"])   # из w33_gh_hiprec
L2 = nDT2 + 2*nDT*K*rho + (K*rho)**2
qv = L2 / delta**4
ok_q  = abs(float(qv)-float(q_json)) < ...   # перерасчёт из архива == поле JSON
ok_sp = float(qv) < 1
```
Тогда подмена `nDT2` ломает либо `ok_q`, либо `ok_sp`.

## Латентные находки на пойманных порчах (T02, T03)

Эти порчи пойманы, но «не тем местом», и при малейшем послаблении превратятся
в дыры — поэтому их надо зафиксировать отдельно.

**T02 (M3_chosen 1834→123479).** Поймано строкой `[MISMATCH] M3_chosen == 1834`
— это **строковое сравнение с литералом** `"1834"`. При этом пересчёт `P_ALL`
использует **захардкоженное** `mpf(1834)` в `QCOEF`, а не `m3["M3_chosen"]`,
так что строка `[OK] P_ALL пересчитан == P_all_levels_upper` остаётся зелёной
при любой подмене `M3_chosen`. Перерасчёт не связан с полем `M3_chosen`
двусторонне. Чинится: в формулу подставлять `mpf(m3["M3_chosen"])` и
дополнительно требовать `M3_chosen == 1834` численно.

**T03 (radius 2e-4 → 1e-4, применимость исчезла).** Поймано строкой
`[MISMATCH] M3 radius == 2e-4` (опять **строковый литерал**). Но проверка
применимости при этом осталась зелёной:

```
[OK] Amax(duhamel_ds) < 2e-4 (радиус M3)     # 1.348e-4 < 2e-4
```

Дело в том, что `ok_amax = (amax < 2e-4)` сравнивает `Amax` с **захардкоженным
`2e-4`**, а не с полем `m3["radius"]`. То есть порча применимости («радиус
стал 1e-4 < Amax, право применять сертификат исчезло») верификатор **по смыслу
не ловит** — ему просто случайно помогает строковый контроль литерала.
Чинится: `ok_amax = amax < float(parse_arb(m3["radius"]))` — читать радиус из
сертификата, а не держать литерал.
